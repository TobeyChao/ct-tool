## 一、新方案是什么

`config-native-zero-copy`（2026-08-25，tasks 全部 `[x]`）已经把运行时改成：

- **原生 C 零拷贝**：`gd_native.cpp` 持有唯一一份配置字节，容器索引 + 固定槽位句柄；Lua/C# 只拿指针
- **自写读取器取代 flatc**：退役 `Google.FlatBuffers`、Lua `flatbuffers/` 运行时、flatc 代码生成
- **C# 侧**：`Config/Native/WireReader.cs`（唯一 unsafe 文件）+ `Config/Gen/*Accessor.cs`（row struct + epoch 校验）
- **Lua 侧**：无状态访问器 + 共享元表 + READER 分发表
- **ct 数据层**：`index` 排序向量、i18n entries 按主键排序、主键唯一性校验

两份 TODO 文档（`Config系统实现分析.md` / `Config系统优化方案-对标参考实现.md`）是在它之上做的
问题清单与优化提案，另有 `Config读取性能实测-字节拼装vs裸cast.md` 做工具链级实测。

**这三份文档的质量很高**：实测有汇编、有复现命令、有平台推断边界；`§五 反向对照`主动记录己方优势；
`§四 明确不建议照搬`把不适用项写死避免反复讨论。下面的意见只针对**它们与 ct 现状的错位**。

## 三、逐条判定：已解决 / 仍有效 / 冲突

### 3.1 已被 canonical 结构性解决（不要再做）

**C8「i18n 与 items 平行化」—— 文档标为「结构性，收益最大」，但在 canonical 路径上问题不存在。**

canonical 没有 i18n 侧表：

- 阶段 2：`_merge_i18n(base_rows, ...)` 在**导出期**把译文并进行（`canonical_export.py:194`）
- 阶段 5：**每种语言发一份完整 bundle**（`canonical_export.py:276-282`）

所以 `ItemAccessor.I18nTable` / `WireReader.SearchEntry(I18nTable, pk, slot)` / `pkSlot` 参数 /
「同序等长」这条 SHALL —— **在 canonical 输出上全都不存在**。C8 要消除的
「读同一行两个文本字段 = 两次一模一样的二分」自然不会发生。

⇒ 按 C8 字面实现，等于**把已经去掉的 i18n 侧表再加回来**。C2 里的「二分那一半」同理消失。

### 3.2 仍有效，但落点在 fabulous-game 而非 ct-tool

**§4.1 / 本目录 `PERF-REPORT.md` §3.1：`GetI32/GetU16` 换 `Unsafe.ReadUnaligned`。**

文档结论正确，我的独立实测同向（RyuJIT x64 不合并字节拼装）。
但要纠正落点：**canonical 的生成器不产出 `WireReader`**。`WireReader` 是 fabulous-game 的
`Client/Assets/Scripts/Config/Native/WireReader.cs`；ct-tool 里那份只是
`test-proj/ConfigAccessorBench/` 的基准副本。这条改的是 fabulous-game。

**原生侧「`gd_native.cpp` 保持现状」的结论我认同**：clang 会把拼装合并成单条 load，
拼装版的 vtable 遍历在 aarch64 下还少一条指令（无符号比较把两个条件折成一次）。
文档这条推断做了实测（NDK clang 12 三目标），是本轮最有价值的验证之一。

### 3.3 仍有效，且属于 ct-tool 的「设计了没接线」

**P6 二级索引**：canonical 已经支持，但导出时被硬编码关掉：

```python
# canonical_export.py:211
model = build_accessor_model(table, (), records=records)   # ← indexes 恒为空元组
```

`build_accessor_model(table, indexes, records)` 本身接受索引；`index_query.py` 也已存在。
且 `Runtime.ByCode` / `Runtime.GroupKey` 是 stub（恒返回 `-1` / `Array.Empty<int>()`）
—— ct-tool 自己的 `REVIEW.md` 已记录这条「生成器信任运行时能力」的契约缺口。

⇒ P6 与 P8 是同一类问题：**能力写好了，出口没接**。

**P7 / B6 枚举类型**：canonical accessor 生成的是

```csharp
public ItemRarity Rarity => (ItemRarity)WireReader.I8(_row, 10);
```

**已经 cast 到具名枚举**，但 `output/generated/csharp/` 每表一个文件、**没有产出枚举声明**
⇒ 业务侧仍要手写 `enum ItemRarity : byte` 才能编译，盲 cast 错位风险照旧。
差的是最后一步：从 `config/types/*.yaml` 的 `values` 生成 `public enum X : byte { ... }`（Lua 同理）。
信息在 canonical 里是完备的，成本低。

**P11 字符串池去重**：文档写「需要确认 ct 的 `binary_writer.py` 是否已经在做」——
模块名已变，但这件事**做了**：`canonical_binary.py` 用的是 `builder.CreateSharedString`。

### 3.4 与 canonical 现状冲突 —— 需要先决策

**P5（版本语义：切 i18n 不动 main、旧行仍有效）与 canonical 的 i18n 模型直接冲突。**

文档把 P5 列为「第二批里最该先想清楚的一条」，理由是它能一次性消灭
stale row / B8 调用点 try-catch / design.md Risk#1。但 canonical 是**每语言一份完整 bundle**，
已实测（`check_bundle_duplication.py`）：

| table | zh | en | ja | en/ja 与 zh |
|---|---:|---:|---:|---|
| ComplexShowcase | 2056 | 2056 | 2056 | **逐字节相同** |
| UIConfig | 520 | 520 | 520 | **逐字节相同** |
| Item | 384 | 392 | 392 | 不同（仅串变，标量全量复制） |
| Quest | 320 | 792 | 912 | 不同（仅串变） |

两处后果：

1. **语言切换 = 换整包 ⇒ 所有行指针失效 ⇒ P5 想消灭的整类问题会全部回来。**
   canonical 下 `data_zh.bin` 与 `data_en.bin` 是两个不同缓冲，`ConfigAccessors.Epoch` 必然递增。
2. **包体按语言数膨胀**。gd 现在 3 语言膨胀 3.29×。换算到 参考实现 规模：
   参考实现 是「1 主包 + 9 语言包」≈ 153 MB；canonical 式 10 份全量 ≈ 680 MB ⇒ **约 4.4×**。

⇒ 若采纳 P5，ct 的 i18n 导出要回到「主表 + i18n 侧表」模型。这是**跨仓库的格式决策**，
且它决定了 C8 是否重新变得相关 —— **必须在 P8/P6 之前定，否则后面全是返工**。

## 四、实证：P8 的前提在当前导出物上不成立

P8 自己写了前提：

> 「同一张表的所有行 SHALL 共享同一个 vtable（导出器不得按行裁剪缺省字段）……
> 否则某些行缺字段产生第二个 vtable，偏移表就错了。」

实测（`check_export_preconditions.py`，对 ct 当前 `gd/output/binary/data_zh.bin`）：

| table | 行数 | 不同 vtable 内容数 | P8 前提 |
|---|---:|---:|---|
| `ComplexShowcase` | 4 | **3** | 不成立 |
| `Item` | 4 | **2** | 不成立 |
| `UIConfig` | 7 | **4** | 不成立 |
| `ItemType` | 3 | 1 | 成立 |
| `Quest` | 3 | 1 | 成立 |

**4 行的表就有 3 个不同 vtable。** 且变化的不只是 offset 字段的槽位，连标量槽位
（如 `Item` 的 slot 4/6/8）在不同行里 offset 也不同 —— 因为行的总大小不同，字段落点就不同。

根因在 `canonical_binary.py:_build_row`：

```python
elif self._is_offset_type(field.type_expr):
    continue  # None-valued string/vector: leave slot absent
```

缺省 string/vector 直接不写槽位 ⇒ 每行的 vtable 布局不同 ⇒ 所有行共享 vtable 的假设破裂。

⇒ **P8 落地前必须先立 SHALL + 导出期校验**，否则把 slot→offset 缓存成 `int[]`
会静默读错字段（且因为 flatbuffers 会去重相同 vtable，这个 bug 只在数据恰好出现缺省值时才暴露，
属于最难查的一类）。二选一：
(a) 导出器恒写满所有偏移槽位（代价：每个缺省 string/vector 多一个 uoffset）；
(b) 放弃 P8，只做 §3.1 的 `Unsafe.ReadUnaligned`。

顺带一提：canonical 的 `WireReader` 里 `BuildFieldOffsets` / `I32At` / `StrAt` / `IndirectAt`
**已经写好但生成器从不调用**（生成的 accessor 一律用槽位版 `WireReader.I32(_row, slot)`）——
所以 P8 在 ct 侧同样是「写了没接线」，且实测预取偏移能把字段读从 1.58 降到 0.81 ns（1.95×）。
**但前提不修就不能接。**

## 五、顺带发现：`output/` 有陈旧产物

`gd/output/fbs/` 里同时存在两代文件：

| 文件 | mtime |
|---|---|
| `Item_i18n.fbs` / `ItemType_i18n.fbs` / `Quest_i18n.fbs` | **2026/8/14** |
| 其余（`types.fbs` / `*.fbs` / `container.fbs`） | 2026/9/10 |

ct-tool 里**已无任何代码生成 `*_i18n.fbs`**（全仓 grep `I18nEntry` / `I18nTable` 无命中源码），
它们是上一代生成器的遗留物，而 `ct export` 不清理 `output/`。

风险：消费方（fabulous-game / `ct deploy`）扫描 `output/` 时会拿到**描述已废弃 i18n 侧表格式**的
schema 文件，正好与本评审 §3.1 的结论相撞 —— 会让人误以为 i18n 侧表还在。
建议 `ct export` 在写出前清理 `output/fbs` 与 `output/generated`（或至少校验目录内无未知文件）。

## 六、优先级：用数据对齐文档与我的实测

文档 §4.1 的判断是「字符串分配是大头，先做 C2/C8，GetI32 往后放」。**数据支持这个判断**：

| 操作 | 实测 |
|---|---:|
| 冷读字符串（ct 现状） | **246.7 ns/行** |
| 字符串解码（绕开缓存） | 52.3 ns/次 |
| int32 字段读 | 1.58 ns/字段 |

冷读字符串比 int 字段贵 **~156×**，所以「先字符串」是对的。但要修正两点：

1. **C8 在 canonical 下不存在**（§3.1），所以「先做 C8」这一半要划掉。
2. **C2 的剩余部分（分配）对应的是 canonical 的 `NStringCache` 冷路径**：
   我实测 ct 冷扫 246.7 ns/行 vs 参考实现 38.7 ns（慢 6.4×），根因是
   `ConcurrentDictionary.GetOrAdd` 每个不同串一次；而稳态下 ct 反而快 3.2×（10.1 vs 32.5 ns）。

**建议顺序**（前三项是决策，不是编码）：

| # | 事项 | 归属 | 说明 |
|---|---|---|---|
| 1 | **定 i18n 模型**：保留 canonical 的「每语言整包」还是回到「主表 + i18n 侧表」 | ct-tool ↔ fabulous-game 跨仓库 | 决定 P5 能否成立、C8 是否重新相关、包体 4.4× 是否可接受。**不定就会返工** |
| 2 | **定 P8 前提**：导出器恒写满偏移槽位，或放弃 P8 | ct-tool | 前提当前不成立（§4） |
| 3 | 清理 `output/` 陈旧产物 | ct-tool | 消除已废弃格式的误导来源 |
| 4 | C2 剩余：字符串缓存（顶掉 C1 的 `_rowPtrs`） | ct 生成器 | 热路径唯一 GC 源；144 ns/行的冷路径改善空间 |
| 5 | `GetI32` → `Unsafe.ReadUnaligned` | fabulous-game | 实测 2.5×（字段读）/ 2.4×（二分），改动小 |
| 6 | P6 / P7 接线：索引 + 枚举类型 | ct-tool | `canonical_export.py:211` 传 `()`；枚举差最后一步 |
| 7 | `gd_native.cpp` 保持现状 | — | 文档实测结论正确，我认同 |

## 七、结论

- **文档的运行时分析（A/B/C 三类问题、汇编级实测、平台推断边界）质量很高，不需要重做。**
- **但它对 ct 的假设过期了**：`config-native-zero-copy/tasks.md` 第 1 节与所有生成器落点
  引用的模块已全部删除，需按 canonical 重新映射。
- **收益最大的 C8 在 canonical 下已被结构性解决**（无 i18n 侧表），照做会走回头路。
- **P8 的前提在当前导出物上已被证伪**（4 行表 3 个 vtable），必须先修导出器或放弃该方案。
- **P5 与 canonical 的 i18n 模型冲突**，且牵动包体（≈ 语言数倍膨胀，参考实现 规模换算约 4.4×），
  这是最该先拍板的一条 —— 文档自己也这么说，只是它没意识到 canonical 已经把这个选择做反了。
