# ct-tool canonical 运行时读取优化策略（v2）与实测

> 基准：`PERF-REPORT.md`（参考实现 原生运行时对标）暴露的差距
> 范围：**只改 ct-tool 自有代码** —— 导出器 `canonical_binary.py`、生成器 `canonical_accessor.py`、
> reader 运行时参考实现 `test-proj/ConfigAccessorBench/{WireReader,Runtime,ConfigReader}.cs`
> 结果：字段读 **1.58 → 0.47 ns（3.4×）**，向量 **17.8 → 5.5 ns（3.2×）**，
> 全表扫描 **8.83 → 4.73 ns（1.87×）**；对 参考实现 的差距由 9.3× 收敛到 2.8×。
> ct 自身测试 **331 passed**，等价性校验 **122,340 个字段值逐字段一致**。

---

## 一、策略：四条改动，一条主线

主线是 **「把 vtable 遍历从热路径上挪走」**。canonical 生成的 accessor 每次读字段都要：

```csharp
WireReader.I32(_row, slot)
  → FieldOffset(obj, slot)
      byte* vt   = obj - GetI32(obj);      // 依赖读 1
      ushort vtLen = GetU16(vt);           // 依赖读 2
      if (slot >= vtLen) return 0;         // 分支
      return GetU16(vt + slot);            // 依赖读 3 → 才拿到 offset
  → GetI32(obj + offset)                   // 依赖读 4
```

参考实现 的定宽行是 `*(int32_t*)(p + 常量偏移)` —— **1 次读**。差距就在这里。

| # | 改动 | 位置 | 解决的问题 |
|---|---|---|---|
| **OPT-1** | **行句柄携带按 vtable 解析好的偏移表** | 生成器 + 运行时 | 字段读 4 次依赖访问 → 2 次 |
| **OPT-2** | `GetI32/GetU16/GetI64/GetF32/GetF64` → `Unsafe.ReadUnaligned` | 运行时 | RyuJIT 不合并字节拼装（4 读 3 移位 3 或） |
| **OPT-3** | accessor 缓存 `ConfigTable` 句柄（带世代守卫） | 生成器 | 每次查找 2 次字符串哈希字典 |
| **OPT-4** | `NArray<T>` 空值兜底移出索引器 | 运行时 | 索引器内无条件分支阻断 JIT 向量化 |

### OPT-1 的关键设计：不要求整表共享 vtable

fabulous-game 的 P8 提案要求「同一张表的所有行 SHALL 共享同一个 vtable」，并把这列为落地前提。
**实测这个前提在 ct 当前导出物上不成立**（`check_export_preconditions.py`）：

| 表 | 行数 | 不同 vtable 内容数 |
|---|---:|---:|
| `ComplexShowcase` | 4 | 3 |
| `Item` | 4 | 2 |
| `UIConfig` | 7 | 4 |
| 基准表 `ItemBench` | 6685 | **16** |

根因是 `canonical_binary.py:_build_row` 按行裁剪缺省槽位（`continue  # None-valued string/vector`），
且标量槽位在值为默认值 0 时也不写（`PrependInt32Slot(.., 0)` 的语义），
所以**同一字段在不同行里的 offset 本来就不同** —— 任何「整表解析一次 int[]」的方案都会静默读错。

**本策略的做法**：偏移表按 **vtable 身份**解析并记忆化，行句柄携带自己那份：

```csharp
// ConfigReader.cs —— 一张表通常只有 1~16 个不同 vtable，线性小表足够
public int[] OffsetsFor(IntPtr row, int maxSlot) {
    nint vt = (nint)((byte*)row - WireReader.GetI32((byte*)row));
    for (int i = 0; i < _vtCount; i++)
        if (_vtCache[i].Vtable == vt) return _vtCache[i].Offsets;
    int[] offsets = WireReader.BuildFieldOffsets(row, maxSlot);
    ... 加入缓存 ...
}
```

```csharp
// 生成物：行句柄带 _off，字段读退化为「查表 + 一次加载」
internal ItemBenchRow(IntPtr row, int[] offsets, int version) { ... }
public int Type      => WireReader.I32At(_row, _off[8]);
public string Name   => new NString((byte*)WireReader.IndirectAt(_row, _off[6]), _version);
public NArray<int> Tags => new NArray<int>((byte*)WireReader.IndirectAt(_row, _off[30]), _version);
```

**代价**：行句柄从 16B 涨到 24B（`IntPtr` + `int[]` + `int`），仍是零堆分配的 `readonly struct`；
`ByID`/`ByIndex` 多一次 `OffsetsFor`（vtable 指针读 + 1~16 次比较）。实测这次额外开销
被字典查找的移除抵消有余（见 §三）。

**收益**：不依赖导出器任何格式保证，对现存产物直接生效，也不需要 `config-table-export` 新增 SHALL。

## 二、正确性是先验证的，不是事后补的

OPT-1 最危险的失败模式是「读错字段而不崩」。所以先写了等价性校验
（`Verify.cs`，`dotnet run -- verify`）：对每一行的每个字段，**同时**走偏移表路径和 vtable 路径，
逐值比对。

```
表内不同 vtable 个数: ItemBench=16
已校验字段值: 122,340
[PASS] 偏移表路径与 vtable 路径逐字段等价
```

覆盖：int32 / float32 / bool / 缺省 string（含 null 语义）/ `vector<int32>`（长度 + 逐元素）/
`vector<string>` / 嵌套 record 指针 / ArrayBench 的 5 个向量。

**16 个不同 vtable 下逐字段一致** —— 这就是「不要求整表共享 vtable」这一设计主张的实证。

### 过程中发现自己引入的一个回归（已修）

第一版把表句柄缓存成 `static ConfigTable _table` 后，**整套 bin 换代时缓存不会失效** ——
旧代码每次查字典总是拿到新表，缓存版会继续用已被 `Dispose()`（`GCHandle.Free()`）的旧缓冲，
变成悬垂指针。修法是给缓存加世代守卫：

```csharp
internal static ConfigTable Table {
    get {
        ConfigTable t = _table;
        if (t != null && _tableVersion == TableVersion.Current) return t;   // ← 世代守卫
        Resolve();                                    // _table = Runtime.Table(...);
        return _table;                                // _tableVersion = TableVersion.Current;
    }
}
```

实测零成本（`ByID` 42.86 → 42.24 ns，在噪声内）。

### 四条改动各自的贡献（诊断场景实测）

| 诊断场景 | ns/字段 | 说明 |
|---|---:|---|
| 生成 accessor（现状，槽位版） | 1.58 → **0.47** | OPT-1 + OPT-2 合计 |

## 四、剩余差距：字符串是唯一的大头

**冷扫 6685 个不同字符串：ct 241 ns/行 vs 参考实现 38.8 ns/行（6.2×）—— 本次优化对它零改善。**
根因是 `NStringCache` 的冷路径：

```csharp
if (_cache.TryGetValue(key, out var s)) return s;   // ConcurrentDictionary<nint, string>
s = Encoding.UTF8.GetString(ptr + 4, len);
return _cache.GetOrAdd(key, s);                     // ← 每个不同串一次，含锁/桶分配
```

对比 参考实现 的 i18n 路径（`Config.GetI18N`）**完全不缓存**，只是 `Encoding.UTF8.GetString`。
稳态下 ct 靠驻留反超（7.43 vs 35.64 ns，快 4.8×），但**首次全扫是纯亏**。

这是当前唯一「比 参考实现 慢一个数量级」的项目，也是文档 `Config系统实现分析.md` §C2 指向的同一处。
建议方向（未实施）：

1. `ConcurrentDictionary` → `Dictionary` + 世代失效：加载后的首次批量访问是**单线程**的，
   只读并发契约可以用「世代切换时整体替换引用」来满足，而非逐 op 的并发字典；
2. 或对「一次性全扫」调用点提供免缓存入口（`WireReader.StrAt` 已经是绕过版，实测 44.7 ns）；
3. 更彻底的是 per-field `string[]` 缓存（长度 = `Count`，`Invalidate()` 清空）——
   零解码、零字典，代价是 `Count × 8B` 常驻。

## A.2 要做到「差不多」，还剩三步

### 第 1 步：定宽布局（导出器，**要 spec 决策**）—— 代价已修正

#### 与 flatbuffers 规则的关系：不冲突，也**不需要 `array`**

`uniform=True` 不改变任何字段类型：每个字段仍是普通的 `table` 字段，只是**每个槽位都无条件写出**，
使所有行产出逐字节相同的 vtable。定宽的目标是「字段偏移恒定」，只要 vtable 一致就成立，
**不需要把载荷内联**。

`array`（`[T:N]` 定长数组，flatbuffers 2.0）的作用是把向量内容内联进父表 —— 本方案用不到它，因为：

- 参考实现 自己的数组也是**外置**的：`NArray<int>(dataPointer + p->areas, ...)`，`p->areas` 是相对
  表数据池的 int 偏移，数组数据不在行内；
- 所以「行 = 标量 + uoffset 的定宽块，字符串/向量外置」正是 参考实现 `_Data` 的形状，两边同构。

（`array` 在别处确有价值，见本节末「定长向量」。）

#### 体积代价：**取决于字段填充率**，此前文档里的「+1.6%」是错的

那一版是在一张 **100% 填充**的合成表上量的。实测填充率扫描（22 字段 / 5000 行）：

| 字段填充率 | 常规 B/行 | 定宽 B/行 | 膨胀 |
|---:|---:|---:|---:|
| 5% | 33.5 | 109.2 | **3.26×** |
| 25% | 54.4 | 114.0 | 2.09× |
| 50% | 80.4 | 120.0 | 1.49× |
| 75% | 106.4 | 126.0 | 1.18× |
| 100% | 131.9 | 131.9 | 1.00× |

（`ItemBench` 落在最右列，所以当初只有 +1.6%。）

根因：定宽把「缺省 = **不占字节**」变成「每字段**恒占 4 字节**」。
`canonical_binary.py` 现在对默认值走 `PrependInt32Slot(.., 0)`（值 == 默认则不写槽位），这是免费的。

**但这不等于相对 参考实现 的退步** —— 参考实现 的行**本来就恒等于 `字段数 × 4`**
（`Item` = 36 × 4 = 144 B/行），无论数据多稀疏。定宽是把 ct 的体积模型换成 参考实现 的模型。

#### 收益（实测，字面量访问器）

| 场景 | 偏移表 | **字面量** | vs 参考实现 |
|---|---:|---:|---:|
| int32 字段读 | 0.47 | **0.22** | 2.87× → **1.38×** |
| `vector<int32>` 求和 | 1.90 | **1.47** | 1.56× → **1.20×** |
| float32 / bool | 1.27 / 0.90 | ~0.8 / ~0.4（同构推算） | 1.66× / 1.42× → ~1.0× |

#### 语义变更（与体积无关，必须单独拍板）

缺省值从「absent → `null`」变为「default → `""` / `0` / 空向量 / 零值 record」。
这与 参考实现 一致（它的定宽 int 槽没有「缺省」概念），并顺带消掉一类空指针风险
（当前 record 子行对缺省字段在 Release 下无兜底）。

#### 建议：按表决定，而不是全局开

既然代价正比于**稀疏度**、收益对所有表相同，最优解是**逐表选择**：

- 导出时统计每张表的字段填充率（`ct status` / layout manifest 已有数据可复用）；
- 填充率高于阈值（实测 75% 以上膨胀 ≤1.18×）→ 该表 `uniform=True` + 生成字面量访问器；
- 稀疏表 → 保持变长 + 偏移表访问器。

两条代码路径本次都已实现并各自实测通过（偏移表版 `render_csharp_accessor` 默认输出；
字面量版见 `gen_literal_accessor.py`），所以逐表切换的成本主要在导出器侧的填充率统计与
「生成器按表二选一」的接线。

#### 附：`array` 真正能用的地方 —— 定长向量

若某张表的 `vector<T>` **长度恒定**，用 `[T:N]` 内联可省掉一次 uoffset 解引用 + 一次潜在 cache miss，
使 ct 在这一项上**反超** 参考实现（参考实现 的数组同样外置）。但：

- flatbuffers 定长数组只允许标量 / struct 元素，不允许 string / table；
- ct 现在的 `vector<T>` 是真正变长的（`excel_columns` 固定的是模板列数，不是数据长度）；
- 因此需要引入新的 schema 概念「定长向量」，只在长度确实恒定的字段上启用。

这是一项**独立**的优化，不是定宽的前提。

### 第 2 步：主键哈希索引（导出器）

参考实现 每张表内建 `idTableOffset` 哈希表（`GlobalConfigData.h`），`ByID` 是 O(1)；
ct 用排序向量二分，6685 行 = 13 次探测。已定位到纯查找成本：
预解析 + 直接加载的裸二分 = **22.5 ns**，与全路径 31.3 ns 的差是 `ConfigTable` 包装与访问器开销。

**再加一个哈希向量即可**（照现有 `index` 向量的样子），预计 `ByID` 落到 ~12 ns ≈ **1.1×**。
代价：每表多一份哈希桶 + 索引字节。

### 第 3 步：接受两项追不平的

| 项 | 现状 | 为什么追不平 |
|---|---|---|
| 字符串解码本身 | 1.38× | `Encoding.UTF8.GetString` vs 原生 `memcpy` + 就地解码；托管侧固有开销 |
| 加载的托管读盘 | 1.30× 端到端 | `File.ReadAllBytes` 整包托管分配；parse 本身已 **0.95×**（比原生快） |

## A.3 一句话结论

**做了 OPT-5/OPT-6 之后，「耗时差不多」已经在多数维度成立**：
全表扫描和字符串热读 **ct 更快**，端到端行访问 1.98×，冷扫 1.88×，加载 parse 0.95×。
再叠加定宽布局（+1.6% 字节）与哈希索引，**除字符串解码（1.38×）外全部可进 1.2× 以内**。

## A.4 一处必须记住的测量陷阱

向量场景第一版得出「ct 慢 3.2×」，实际是**不公平比较**：参考实现 `Skill.areas` 平均长度
**1.2** 个元素，而基准表是 **12** 个 —— 等于让 ct 干 10 倍的活。长度对齐后是 **1.20×**。
同类的污染还有 `i % 非2的幂` 的整数除法（见 §六测量提示）。
**做读取性能对标时，字段数、向量长度、字符串长度分布都必须先对齐，否则得到的是数量级级别的错误结论。**

## B.1 头号问题：行访问 22.97 ns 里，**22.5 ns 全是二分查找**

| 拆解步骤 | ns | 说明 |
|---|---:|---|
| 生成的 accessor `ByID` + 3 字段读（端到端） | **22.97** | 现在是 1.98× |
| ├ 表句柄解析（世代守卫 + 缓存命中） | ~0.3 | OPT-3 已消掉字符串字典 |
| ├ **index 二分查找** | **22.49** | **几乎全部** |
| └ 3 次字段读 | ~0.7 | 0.22 × 3 |
| 参考实现 `ConfigByID` + 3 字段读 | 11.58 | |

**22.49 ns ÷ 13 次探测（log₂ 6685 ≈ 12.7）= 1.73 ns/探测 ≈ 5 个 cycle。**
这个数字本身已经很紧（每次探测：算下标 → 加载 key → 比较 → 分支），**二分查找没有多少可挤的**。

**根因是算法复杂度差异，不是实现质量**：参考实现 每张表内建 `idTableOffset` **哈希表**，`ByID` 是 O(1)（约 1~2 次探测 + 哈希）。

### 怎么改

| 方案 | 预期 | 成本 |
|---|---|---|
| **A. 导出加哈希索引**（照现有 `index` 向量的样子再加一个桶表） | `ByID` ~22.5 → ~10-12 ns，**端到端 ~1.0-1.1×** | 每表多一份桶 + 索引字节；导出器 + 生成器各改一处 |
| B. 键域稠密时改用直接寻址数组（`maxId-minId < 4×count`） | O(1)，无哈希 | 导出器加一个启发式；对 `Res` 这类顺序 id 的表最划算 |
| C. 加 1~4 项行缓存（`id == _lastId` 直接返回） | 命中时 ~1 ns | 约 10 行；但对**随机**访问无效，只对「同一 id 反复查」的真实游戏模式有效（UI 每帧刷同一行）。需注意只读并发下要么 thread-static 要么不加 |

**推荐 A（必要时叠加 C）**。这是当前最大的一块，且收益确定。

## B.2 二号问题：字符串冷扫 72.82 ns = 43.9 ns 解码 + **28.9 ns 缓存插入**

| 拆解步骤 | ns | 说明 |
|---|---:|---|
| 字符串冷扫（走缓存） | **72.82** | 1.88× |
| ├ 解码本身（绕开缓存实测） | **43.93** | 1.38× —— 托管 `Encoding.UTF8.GetString`，接近地板 |
| └ **缓存插入** | **28.9** | `Dictionary` + 仅 miss 时加锁（OPT-6 后已从 ~165 降下来） |
| 参考实现 冷读（**完全不缓存**） | 38.66 | |
| ct 热读（缓存命中） | 9.28 | 0.29×，靠缓存反超 3.4× |

**问题在于缓存的数据结构选错了**：现在是「按字符串**指针地址**做 key 的全局字典」，
每次 miss 都要哈希 + 加锁。而配置串的访问天然是「(表, 字符串字段, 行下标)」的。

### 怎么改：per-field `string[]` 缓存

生成器为每个字符串字段产出一个按行下标的数组：

```csharp
private static string[] _nameCache;        // 长度 = Count，世代切换时整体丢弃

public string Name
{
    get
    {
        string[] c = _nameCache;
        if (c == null || _cacheVersion != TableVersion.Current) { c = ResetNameCache(); }
        string s = c[_rowIndex];
        if (s != null) return s;
        s = /* 解码 */; c[_rowIndex] = s; return s;
    }
}
```

| | 现在 | 改后（预计） | 参考实现 |
|---|---:|---:|---:|
| 冷扫 | 72.82 | **~46** | 38.66 |
| 热读 | 9.28 | **~2** | 32.03 |

- **冷扫 → ~1.2×**：去掉哈希与锁，只剩「数组存 + 解码」
- **热读 → ~0.06×**：一次数组下标；比现在的指针字典更快
- **内存**：每字符串字段 `Count × 8 B`。6685 行 × 3 字段 ≈ 160 KB
- **顺带消掉一个已知隐患**：指针做 key 在「整套 bin 换代后 GC 复用地址」时会命中陈旧条目；
  行下标做 key + 世代整体丢弃从根上不存在这个问题

行下标需要行句柄携带（`ByID` 走 `index` 向量时拿到的原始行下标，`ByIndex` 直接用入参），
本次 OPT-1 的行句柄已经是「指针 + 偏移表 + 版本」，再加一个 `int` 即可。

## B.3 三号问题：字段读 0.47 → 0.22 ns，**要动导出器且有体积代价**

见附录 A 第 1 步（含填充率代价表）。要点复述：

- 现状 0.47 ns：`_off[slot]` 数组加载（含越界检查）+ 空值判断 + 值加载
- 字面量 0.22 ns：`*(int*)(row + 52)`，一条加载 —— **1.38×，基本追平**
- 前提是定宽布局（同表单一 vtable），体积代价 **按填充率 1.00× ~ 3.26×**
- 建议**逐表开关**：填充率 ≥75% 膨胀 ≤1.18×，稠密表开、稀疏表不开

**残余的 0.22 vs 0.16**：行句柄是 16 字节 struct（`IntPtr` + `int` + padding）按值传递，
而 参考实现 的是一根 8 字节裸指针。把行句柄里的 `IntPtr _row` 换成 `byte* _p` 可省掉一次
IntPtr→指针转换，预计 0.22 → ~0.18。

## B.4 四号问题：加载 82.8 ms 里 **22 ms 是托管读盘 + 2000 次 byte[] 拷贝**

| 拆解 | ms |
|---|---:|
| `File.ReadAllBytes`（105.8 MB） | **19.9** |
| `LoadBundle`（解析 2000 表 / 692k 行） | **60.3** |
| 其它 | ~2.6 |
| 合计 | 82.8（参考实现 62.6，1.30×） |
| 参考实现 TableInit（**含原生读盘**） | 62.6 |

注意 ct 的 **parse 已经比 参考实现 的「读盘 + 解析」更快（0.95×）**，多出来的全是托管侧
「整包读进 `byte[]` + `ReadBundle` 里给每张表再做一次 `byte[]` 拷贝」。

### 怎么改：单缓冲视图

`WireReader.ReadBundle` 现在对每张表 `new byte[dataLen]` 再逐字节拷。
改成「整包一份 pinned buffer + 每表 `(offset, length)` 视图」：

- 消除 2000 次托管分配与拷贝（也消掉 2000 个 GC 对象）
- 读盘与解析合并为一次遍历
- 预期 82.8 → **~63 ms，追平（1.0×）**

顺带：`ConfigTable` 目前对每张表各持一个 `GCHandle`；改成共用整包句柄后也少 2000 个 pin。

| # | 动作 | 预计收益 | 位置 | 风险 |

# 附录 D：OPT-9 单缓冲视图 —— 加载反超 2.3×

> **OPT-9**：整套 bundle 只 pin 一次，各表句柄是同一缓冲内的 `(offset, length)` 切片。
> 取代原先「`ReadBundle` 给每张表 `new byte[]` + 逐字节拷贝 + 每表一个 `GCHandle`」。

## D.1 结果

| | 改前 | **改后** | 参考实现 |
|---|---:|---:|---:|
| `File.ReadAllBytes`（105.8 MB） | 19.9–31.0 ms | 26.1 ms | 计入下一行（原生读盘） |
| **`LoadBundle`（解析 2000 表 / 692k 行）** | **61.9 ms** | **0.6 ms** | — |
| 端到端 | 81.5 ms | **26.7 ms** | 62.5–65.1 ms |
| **比值** | 1.31× | **0.41–0.44×** | — |
| 表数量级 | 2000 次分配 + 2000 GCHandle | **1 次 pin** | — |

`LoadBundle` 降到 0.6 ms 的原因是：**它是彻底惰性的** —— 只解析容器表拿到 2000 个切片位置，
不做任何逐行工作。所有 per-row 成本（偏移表、哈希索引、字符串缓存）都在首次访问时按需解析。
索引本身是**导出期烘进二进制**的，所以加载不需要建索引 —— 而 参考实现 的 `TableInit`
是 92 ns/行（≈63 ms / 691k 行），看起来把索引构建放在了加载期。

（端到端比值 0.41× 略优于「读盘 + 解析」的 26.7/62.5 = 0.43×，差异来自 参考实现 读的是
146.8 MB（10 个语言包）而 ct 只读 105.8 MB 单语言包。**按字节比：ct 3960 MB/s vs 参考实现 2316 MB/s。**）

## D.2 生命周期契约

```
ConfigBundle     整套缓冲 + 唯一 GCHandle；ConfigReader 持有 _current
  └ ConfigTable  视图（Table = bundle.Base + offset）；Dispose() 为空操作
```

- pin 只在**整套边界**创建/释放：`ConfigReader.LoadBundle`（释放上一套）与 `ConfigReader.Unload`
- `ConfigTable.Dispose()` 在视图模式下**不释放 pin**（pin 归 `ConfigBundle` 所有），
  这样 `Runtime.Register` / `Runtime.Clear` 的既有语义完全不变
- 单表模式（`new ConfigTable(name, bytes)`）保持原样，仍自持一个 pin


## D.4 顺带修掉：基准生成脚本的「双重构建」

`gen_ct_bench_tables.py` 原先把每张表构建了**两次** —— 一次写单表 `.bin`，一次进 `bench_bundle.bin`。
模块级 `rng` 是共享推进的，两次调用产出**不同数据**，于是「视图 vs 单表」一致性校验误报 6685 处不一致。
改成构建一次、复用同一份 bytes。**这是校验脚本先发现的**：如果没写这个校验，这个不一致会一直潜伏，
并且会让后续所有「单表 vs bundle」类比较失去意义。

## D.6 唯一剩下的决策点

字段读（int32/float/bool/向量）是现在唯一 >1.4× 的一组，解法只有一个：
**逐表定宽布局 + 字面量偏移**（附录 A 第 1 步 / 附录 B.3），代价是按字段填充率的体积膨胀
（1.00× ~ 3.26×）。其余全部已达或超过 参考实现。
