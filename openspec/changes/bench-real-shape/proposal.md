## Why

现有基准夹具（`native/fixtures/bench/generate.py` 的 S/M/L）每张表同构：固定 20 列、每表相同行数、3 种语言。用 S/M/L 冷全量三点插值出的成本模型是 `time_ms = 744 + 7.51×表数 + 0.00540×单元格`；把它外推到真实工作区形状（2,027 表 / 6,953,587 槽位）只给出 **26.9s**。

实现本变更后实测（同一台机器、回归档 818 表 / 249,569 行 / 3,709,512 槽位）：

| 口径 | L 档（现状） | 回归档 `r`（真实形状） | 差异 |
|---|---|---|---|
| 冷全量（中位） | 101.3s | **422.8s** | 4.2× |
| 热（输入无变化） | 54.5s | **153.2s** | 2.8× |
| 产物文件数 | 607 | **10,646** | 17.5× |
| 数据单元格 | 18.48M | 3.71M | 0.20× |

也就是说：真实形状的冷全量比 L 档贵 4.2 倍，却只有 L 档 **20%** 的单元格——按单元格线性外推会低估 **15.7×**。热场景（几乎不做数据工作）仍占冷全量的 36%，说明固定开销是真实工作区成本的主要成分之一，而这部分在按单元格外推时被完全忽略。现有夹具无法暴露这一点，因为它每张表都同构。

## What Changes

- 新增两档「真实形状」夹具，形状取自真实工作区的**实测分布**而不是等宽参数：
  - **bench-r**（常规回归）：818 表（654 Enum + 164 Config，其中 12 张巨型表强制纳入、152 张按分层抽样）/ 249,569 行 / 3,709,512 槽位 / 127 个 i18n 字段（每语言 117,146 条）/ 10 语言；模型 fixed 占比 22.8%。
  - **bench-r-full**（手动专项，不进 CI）：2,027 表（1,373 Config + 654 Enum）/ 691,518 行 / 6,953,587 槽位 / 816 个 i18n 字段（每语言 301,656 条）/ 10 语言；模型 fixed 占比 28.4%。
- 新增**冻结形状清单** `native/fixtures/bench/shape-r.json`：由真实工作区的两份留档（运行时行数 dump ⋈ 导表期类清单/字段语法）按类名合并冻结进仓库，并附一次性 provenance 命令。夹具生成期 SHALL 只读该清单，不读 `design-data` / `dev_trunk_ref` 或任何真实工作区。
- 夹具生成器新增 `--size r` / `--size r-full`，由原生生成路径实现（不调用 `ct/.venv` 入口）；`ct-xtask` 的夹具入口接受这两个尺寸。
- 形状维度从硬编码改为按实测分布：每表嵌套深度（决定表头行数，实测 2–8 行）可变、向量字段横向展开列、Enum 表按真实工作区口径建成独立表、跨表 ref 画像（含 `Res` 这种 532 字段引用的 hub）、内联 struct 与引用边比例。
- 随夹具登记**已知偏差**（不假装覆盖）：译文条目口径 A 取"每 i18n 单元格一条"（为真实已翻译条目的约 1.6 倍）、i18n 文件布局与真实工具不同（per-table vs per-language 聚合）、真实工作区多表共享工作簿而内核要求一表一工作簿、分区域列（`MultiArea`）能力缺失故不建模、`animevent`/track 二进制排除、向量展开列宽为确定性合成值、bench-r 行数尾部高配。
- 明确**不动**：现有 s/m/l 夹具及其门槛保持不变；不改产物字节与业务代码；不改性能判定语义（bench-r 复用既有的「参照不在位时走本机留档回归判定」路径）。

## Capabilities

### New Capabilities

- `benchmark-fixtures`: 基准夹具的形状真实性契约——两档夹具的构成与用途、冻结形状清单的来源与不可变约束、生成期的可复现性（固定种子、不依赖真实工作区或 Python 参照在位）、以及必须随夹具登记的已知偏差。

### Modified Capabilities

无。性能门槛数值与「参照不在位时改用本机留档回归判定」的语义已由 `rust-native-core` 的 `native-core-runtime` 规格覆盖，本变更只新增夹具档位并复用该判定路径，不改变任何既有 requirement。新档位的门槛数值待首次实测后再单独提案修订。

## Impact

- 新增：`native/fixtures/bench/shape-r.json`（冻结清单，含 2,027 张表的字段语法、引用边与两档构成）、`native/fixtures/bench/README.md`（形状来源与偏差登记）、实测后的 `native/docs/baseline/bench-r-<平台>.json`。
- 修改：`native/crates/ct-xtask/src/shape.rs`（冻结与自检）、`native/crates/ct-xtask/src/real_fixture.rs`（原生夹具生成）、`native/crates/ct-xtask/src/fixtures.rs`（尺寸分发）、`native/crates/ct-xtask/src/bench.rs`（新尺寸的判定接线）、`native/crates/ct-excel/src/template.rs`（带数据行的模板构建入口）。
- 不影响：`ct/` 与原生内核的业务行为、产物字节、现有 S/M/L 留档与门槛；s/m/l 仍走既有 Python 生成脚本，r/r-full 走原生路径。
- 风险：bench-r 生成成本高于 L 档（164 张 config 表各一个工作簿，其中 12 张巨型表共约 24 万行需写入）；`bench-r-full` 生成耗时与磁盘显著更高，因此不进 CI。
