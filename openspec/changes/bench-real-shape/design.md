## Context

现有夹具生成器 `native/fixtures/bench/generate.py` 只接受 `--size s|m|l`，表结构写死为 20 列（`scalar_fields`），每表行数相同（`SIZES = {"s": (10, 100), "m": (50, 2000), "l": (100, 10000)}`），语言为 `zh + en + ja`；`ct-xtask` 侧 `fixtures.rs` 的白名单同为 `["s","m","l"]`。夹具生成调用隔离 venv 里的 Python 参照入口（`ct_exe()` → `ct/.venv/Scripts/ct.exe`）来跑 `gen-template` 与 `i18n sync`。

形状来源是两份留档，**口径不同，冻结时各取所长**：

- `test-proj/RefConfigBench/ref_table_shapes.json`（2,012 张表的 rows / fields / i18n / int_arr / str_arr）与 `ref_tables.json`，来自 `dev_trunk_ref` 的运行时 dump（该 checkout 本机已不在位）：**只取每表行数**。
- `D:\dev_trunk_harmony\design-data\ExcelRecord.json`（2,027 个类的字段类型语法与引用关系；1,373 Config + 654 Enum）与对 `Excel/` 662 个 xlsx 的实测扫描（2,186 sheet、15,234,404 非空单元格、表头行数分布）：**取字段语法、i18n 标记、引用边与嵌套结构**。

冻结时核实的两处口径差异（已记入清单 provenance，不作为权威计数）：

- 字段数：dump 11,217 vs 类清单 11,314（1,310/1,362 张表完全一致，余下有 ±1 与个别 -26 的偏差，来自嵌套 struct 的计法）。
- i18n 字段数：dump 1,630 vs 类清单 815（同表常为 2 倍关系）。若沿用 dump 口径，口径 A 的译文条目会被放大到真实的 3.3 倍；改用类清单的 `[I18N]` 标记后为真实的约 1.6 倍，与实测 `EN.json` 的 185,265 条自洽。

约束来自仓库既定规则：原生内核与桌面的验收路径不得依赖 `ct/` 在位；真实 `gd/` 不得作为写入夹具；`ct/` 只在需要重建夹具时作为可选的资料生成器。

内核侧的形状能力（已核实）：

- `ct-excel/src/layout.rs` 的 `header_rows = max_depth * 2`：表头行数由 schema 嵌套深度决定，天然可变（扁平表 2 行，含一层嵌套 record 4 行）。
- `ct-excel/src/template.rs` 通过自定义属性 `ct_header_rows` 记录表头行数。
- 一表一工作簿是硬约束：`native/tests/compat/tests/schema_save.rs` 明确拒绝两个 Table 指向同一工作簿（仅大小写不同也算冲突）。
- `native/` 全仓库没有任何 `MultiArea` 语义。

## Goals / Non-Goals

**Goals:**

- 让「表 × 语言」固定开销成为可测量量，并给出真实形状档与现有 L 档的可比数字。
- 两个档位共用同一套形状规则与同一份冻结清单，只有规模不同。
- 夹具生成不依赖 `ct/` 在位，也不依赖任何真实工作区 checkout。
- 形状来源、抽样规则与未建模维度都可追溯（清单 + 偏差登记）。

**Non-Goals:**

- 不修改 s/m/l 三档及其门槛、留档与判定口径。
- 不新增或修订性能门槛数值（`native-core-runtime` 的 `Reproducible performance acceptance` 保持原样；新档位的门槛待首次实测后单独提案）。
- 不把夹具用于产物正确性对照（夹具是性能与形状工具，不是 golden 来源）。
- 不建模分区域列、多表工作簿、动画事件曲线与轨道二进制。
- 不改动业务代码与产物字节。

## Decisions

### D1 两档而非一档

回归档 `r` 进常规回归，全量档 `r-full` 只在显式请求时执行。备选是全量档单独一档（2,027 表生成与测量成本会让常规回归不可接受）或只做抽样档（无法验证"形状外推"是否成立，也无法在真实表数下复核 per-table 项）。两档共用形状规则与清单，规模参数不同。

### D2 抽样 = 全 Enum + 分层抽样 + 强制巨型表

- 全 Enum（654 张）：真实占比 32% 的表数，且真实工作区把它们当独立表逐表导出（各带 id/codeName/designName），在夹具里也建成表。
- 分层抽样 152 张：按（行数桶 × 字段桶）分层，每层至少 1 张，按层规模比例分配；层内以「是否引用强制 hub」优先、再按 `splitmix64(seed ^ fnv1a(表名))` 排序选取。落地后实测：薄表（≤10 行）占 40.9%，与全量的 43.3% 之比为 94%（自检阈值 80%）。
- 强制 top-12 by 槽位：`Res`（134,198 行）单表占全量槽位的 15.4%。备选是纯比例抽样或按槽位加权抽样，两者都会让"是否命中 Res"决定整轮量级，run 间方差不可接受。
- 选择规则用哈希排序而不用 RNG：清单可以在任何语言/版本里复算出同一份表集合，不需要复刻某个 PRNG 的序列。

### D3 冻结形状清单 `shape-r.json`

由 `ref_table_shapes.json`（每表行数）与 `ExcelRecord.json`（字段类型语法、i18n 标记、引用边、嵌套结构）按类名合并后冻结进仓库；Enum 类按真实工作区口径建成独立表（id/codeName/designName），因此指向 Enum 的字段成为 `int32 + ref`。清单含每表的字段、行数、嵌套深度、两档构成与全部计数。备选是生成期直接读 `design-data`：违反"验收路径不依赖外部 checkout"，也无法在 CI 复现。冻结是一次性 provenance 步骤（`xtask bench-shape-freeze`），需要两份外部留档；生成期只读清单。

### D4 生成后端改用原生路径

新档位由 `ct-xtask` 直接调用原生库入口（`ct-domain` / `ct-excel` / `ct-app`：`build_template_with_rows`、`build_layout`、`LayoutManifest`、`i18n_sync`），不调用 `ct/.venv` 的 Python 入口，也不需要预编译的 CLI。理由：s/m/l 的 `ct_exe()` 会把参照实现变成夹具生成依赖，而 `ct/` 已明确降级为可选。代价是 s/m/l 的既有生成路径与新档次不一致——这需要同步 `native/README.md` 的说明，但 s/m/l 本身的生成方式不在本次改动范围内。

为此在 `ct-excel` 增加了 `build_template_with_rows`：与既有 `build_template` 同一实现（`build_template` 以空行数组调用它），只多写数据行，不改任何既有行为。

### D5 表头深度由嵌套深度驱动，不单独参数化

不引入"header_rows 参数"，而是让抽样的表带上真实的嵌套深度分布（扁平 / 一层 record / 两层 record…），由内核既有的 `header_rows = max_depth * 2` 推出表头行数。冻结后的实测分布为深度 1/2/3/4 → 1,302/565/138/22 张表（最大表头 8 行），覆盖多条嵌套路径而不引入内核不支持的形状。

### D6 i18n 口径 A

每个 i18n 单元格都生成一条译文条目。清单口径下全量档每语言 301,656 条（9 语言 2,714,904 条），真实工作区的已翻译条目是每语言约 185,265 条（9 语言 1,446,234 条），即夹具高约 **1.6 倍**。选择理由：口径 A 自洽、可复算、方向保守（宁可高估 i18n 成本）。该偏差必须登记，不得当成"与真实一致"。

### D7 判定路径复用既有语义

回归档沿用 `native-core-runtime` 已定义的"参照不在位时改走本机留档回归判定"：`regression-pass`/`regression-fail` + `baselineMode=archived-run`，不声称配对测量。全量档可以额外跑配对测量（含 Python 参照），但那是手动专项，不进 CI。

## Risks / Trade-offs

- [回归档生成成本高于 L 档：164 个 config 工作簿、约 25 万行由原生模板写入] → 巨型表行数取真实值，但回归档只纳入 top-12；生成结果落在 `native/target/bench/`，需要时才重建。
- [强制纳入 `Res` 使行数尾部高配] → 登记为已知偏差；用薄表占比与分桶对照说明抽样质量，而不是只看总量。
- [D4 让 s/m/l 与新档次生成方式不一致] → 本次只为新档次实现原生生成；s/m/l 的 Python 生成保持现状并在文档里标注"新档次不沿用"。
- [`shape-r.json` 的行数来源是 `dev_trunk_ref`（本机已不在位）] → 清单冻结后不再需要该 checkout；清单 provenance 记录来源与口径，后续若需更新形状必须显式替换清单。
- [口径 A 让译文条目是真实的约 1.6 倍，i18n 场景耗时可能高于真实工作区] → 登记偏差并在报告里同时给出真实工作区的条目基数，避免把夹具数字当成真实预期。
- [表头深度只能到内核支持的嵌套层数，实测最深 8 行] → 按真实嵌套深度分布冻结（当前最大 8 行）；若后续需要更深嵌套，登记为偏差而不是伪造表头行数。

## Migration Plan

1. 先落 `shape-r.json` 与偏差登记文档（纯数据，无行为变化）。
2. 在 `ct-xtask` 里实现原生生成（`shape.rs` 冻结+自检、`real_fixture.rs` 生成），`fixtures.rs` 按尺寸分发，`bench.rs` 判定接线。
3. 首次实测生成 `native/docs/baseline/bench-r-<平台>.json` 留档，据实测结果再单独提案新档位的门槛数值。
4. 回滚方式：新档次是增量入口，删除清单与尺寸分支即可恢复现状；s/m/l 与既有留档不受影响。

## Open Questions

- 回归档实测：冷全量 422.8s、热 153.2s（固定开销占 36%）、产物 10,646 个。**原设计的口径（用 S/M/L 三点插值说「L 档 per-table 占 0.7%」）已被实测否证**：那个 0.7% 是插值模型把 S/M/L 的差异全算进单元格项的结果，同一模型外推回归档会低估 15.7×。后续若要把「固定开销占比」作为门槛，应以「热场景 / 冷全量」这类同档位内部比值定义，而不是跨档位的插值系数。
- 全量档（2,027 表 / 每语言 301,656 条）尚未实测；按回归档的固定开销绝对值外推，其冷全量和磁盘占用都会显著高于回归档，需先实测再决定是否值得作为常规专项。
- 全量档是否需要同时跑 Python 配对测量（取决于 Python 侧在 10 语言、271 万条译文下的耗时是否可接受）。
